# SPEC-300 – Competition Engine

**Version:** 1.0

**Status:** Approved

**Applies to:** STM V2

---

# Purpose

The Competition Engine is the core domain of STM.

Its responsibility is to define, generate, execute and manage sports competitions independently from the specific sport being played.

The engine must be flexible enough to support different competition formats while maintaining a simple and consistent user experience.

---

# Domain Overview

The Competition Engine manages the complete lifecycle of a competition.

```
Competition

↓

Configuration

↓

Entries

↓

Generation

↓

Play

↓

Reports
```

Every competition follows this workflow.

---

# Aggregate Root

The Aggregate Root is:

```
Competition
```

Everything belongs to a Competition.

No object exists independently.

```
Competition
│
├── Configuration
├── Entries
├── Structure
├── Generation
├── Courts
├── Matches
├── Rankings
├── Reports
└── Optimizer
```

---

# Competition Definition

A Competition is defined by:

- title
- description
- workspace
- structure
- play mode
- scoring model
- settings

The definition never changes during execution.

---

# Competition State

Competition state is independent from its definition.

Available states:

```
draft

↓

configure

↓

ready

↓

generated

↓

running

↓

completed

↓

archived
```

The state represents the lifecycle.

It never describes the competition model.

---

# Structure

Structure defines how the competition is organized.

Supported structures:

- Single Elimination
- Double Elimination (future)
- Round Robin
- Round Robin + Playoff
- Round Robin + Playoff + Consolation
- Individual Round Robin
- Swiss (future)
- League (future)

Structure is independent from the sport.

---

# Play Mode

Play Mode defines how competitors participate.

Supported modes:

- Singles
- Doubles
- Individual Doubles
- Teams

Play Mode is independent from Structure.

Every Structure may support multiple Play Modes.

---

# Configuration

Configuration contains all static information.

Examples:

- number of courts
- scoring model
- seeding enabled
- match duration
- maximum rounds
- optimizer settings
- ranking rules

Configuration lives inside:

```
settings
```

---

# Entries

Entries represent participants.

Depending on the Play Mode they may become:

Player

or

Team

Entries remain immutable after generation.

---

# Generation

Generation creates the playable structure.

Generation may create:

Groups

Stages

Matches

Courts

Ranking tables

Qualification rules

Generation is deterministic.

The same configuration always generates the same structure.

---

# Structure Objects

Depending on the selected Structure, the engine may create:

```
Groups

Stages

Brackets

Qualification Rules

Ranking Tables

Matches
```

Not every structure requires every object.

---

# Courts

Courts represent physical resources.

The engine assigns matches to courts.

Courts never know competition logic.

They only know scheduling.

---

# Matches

Matches are executable competition units.

A match contains:

Participants

Court

Status

Score

Winner

Timing

Scheduling

Every competition ultimately becomes a collection of matches.

---

# Rankings

Rankings are generated by the engine.

Ranking algorithms depend on:

Structure

Play Mode

Scoring Model

Optimizer

Ranking implementation is delegated to RPC algorithms.

---

# Reports

Reports are read-only projections.

Examples:

- Standings
- Match Schedule
- Brackets
- Statistics
- Printable Reports

Reports never modify the competition.

---

# Optimizer

The Optimizer generates fair schedules.

The Optimizer knows only:

- Players
- Teams
- Courts
- Time
- Constraints
- Matches
- Rounds

The Optimizer must never contain sport-specific logic.

---

# Competition Workflow

The Competition Engine follows this workflow.

```
Competition

↓

Configuration

↓

Entries

↓

Generation

↓

Play

↓

Reports
```

No phase should be skipped.

---

# Separation of Responsibilities

Competition

Responsible for:

- lifecycle
- workflow
- ownership

Configuration

Responsible for:

- static parameters

Generation

Responsible for:

- structure creation

Matches

Responsible for:

- execution

Reports

Responsible for:

- presentation

Optimizer

Responsible for:

- fairness

---

# Future Extensions

The architecture has been designed to support future features without structural changes.

Examples:

- Swiss System
- League Competitions
- Ladder Competitions
- Team Championships
- Seasonal Rankings
- AI Scheduling
- Public APIs

---

# Design Principles

The Competition Engine follows these principles.

- Competition First
- Workspace First
- Repository Pattern
- RPC for Algorithms
- Mobile First
- DB First
- Stateless UI
- Deterministic Generation

---

# Non Goals

The Competition Engine does not manage:

- Club administration
- Payments
- Memberships
- Court bookings
- Event marketing
- Communication

These belong to external systems.

STM focuses exclusively on competition management.

---

# Implementation Strategy

Implementation follows this sequence.

```
Domain Model

↓

Database

↓

Repositories

↓

RPC

↓

Server Actions

↓

UI

↓

Reports
```

This order is mandatory.

The implementation should never start from the user interface.

---

# Final Objective

The Competition Engine is designed to become a reusable competition framework capable of supporting multiple sports through a single architecture.

Its primary objective is to maximize flexibility while keeping the user experience simple, predictable and maintainable.
